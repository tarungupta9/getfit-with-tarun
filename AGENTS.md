# GetFit with Tarun agent guide

## Start every task from the latest branch state

Production deploys from `main`. Before planning, editing, or reviewing code:

1. Run `rtk git status --short --branch` and identify the checked-out branch and its upstream.
2. If the worktree and index are clean, run `rtk git pull --ff-only` on the checked-out branch.
3. If local work, unmerged entries, or an interrupted Git operation makes a pull unsafe, do not stash, discard, reset, resolve, or overwrite that work. Run `rtk git fetch origin`, compare `HEAD` with the branch upstream, and report whether the branch is ahead or behind. Resolve the repository state with the user before changing overlapping files.
4. Never assume a stale local `origin/*` reference represents production. Fetch before making that comparison.

Use fast-forward-only pulls. Do not create merge commits just to synchronize a task branch.

## Plan with architecture visible

Every implementation plan must give the user an architectural review point before code changes begin. Scale the detail to the change, but always include:

- **Scope and constraints:** the user-visible outcome, affected flows, assumptions, and explicit non-goals.
- **HLD (high-level design):** affected system boundaries, components, ownership of data and business rules, end-to-end data flow, persistence or external-service changes, deployment impact, and major tradeoffs.
- **LLD (low-level design):** files and modules to change, types and interfaces, function or component responsibilities, state transitions, validation and error paths, accessibility behavior, and test/check coverage.
- **Architecture delta:** state which existing architectural decisions remain unchanged and call out every proposed new dependency, service, storage location, runtime integration, or trust boundary.

For a small local fix, the HLD and LLD can each be a few sentences. If there is no architectural impact, say so explicitly. For a material architectural change, present the HLD and LLD and wait for the user's review before implementing it. After approval, keep the implementation aligned with the reviewed design; surface any material deviation before proceeding.

Record lasting product or architecture decisions in a new document under `docs/version-plans/` or `docs/designs/`, as appropriate. Preserve superseded version plans as history instead of rewriting them.

## Current architecture

- The app is a browser-only React 19 prototype built with TanStack Start, TanStack Router, Vite, and strict TypeScript.
- `src/routes/` owns routing and page entry points. `src/features/planner/` owns planner UI and interaction state.
- `src/domain/` owns schemas, types, and the pure deterministic plan compiler. Keep this layer independent of React, browser APIs, and deployment adapters.
- `src/content/` contains versioned, locally bundled exercise, sequence, policy, and safety content. `src/content/index.ts` validates and assembles that content.
- `src/persistence/preferences.ts` is the browser persistence boundary. Only planner preferences may be stored in `localStorage`.
- `public/exercises/{exercise-id}/` contains local exercise posture assets.
- Netlify production builds are configured in `vite.config.ts` and `netlify.toml`; local development does not depend on Netlify platform APIs.
- `src/routeTree.gen.ts` is generated by TanStack Router. Do not edit it by hand.

## Product and trust boundaries

- Keep plan generation deterministic and fail closed for invalid input, incompatible versions, missing content, or an impossible plan. Do not generate a partial or improvised prescription.
- Do not add a runtime LLM, dynamic exercise/video search, unreviewed remote content, or automatic source substitution without an approved architectural change.
- Treat exercise prescriptions, movement cues, posture media, demonstrations, and safety copy as safety-sensitive draft content requiring qualified human review before public release.
- Keep source provenance and review metadata with content. A reachable URL is not evidence that its content is still suitable.
- Do not collect or persist health answers, the generated plan, or disclaimer acknowledgment. Do not add analytics or logging that captures them.
- Preserve the supported audience and scope in the design record: general educational home fitness for apparently healthy adults aged 18–64, without diagnosis, rehabilitation, nutrition advice, or claims that the app can assess movement quality.

## Implementation rules

- Parse untrusted and persisted data with the Zod schemas in `src/domain/schemas.ts`; derive TypeScript types from the domain contracts rather than duplicating shapes.
- Keep duration calculations, exercise selection, progression, and explanation generation centralized in the domain layer. UI components render domain results and must not recreate business rules.
- Preserve stable IDs, deterministic sorting and tie-breaking, version compatibility, duration budgets, required movement-family coverage, and A/B adjacency constraints.
- When changing generated catalogue or policy content, update `scripts/generate-content.mjs` as the source, regenerate the JSON, and validate it. Keep referenced IDs, assets, catalogue versions, policy versions, and safety-copy versions synchronized.
- Maintain keyboard operation, visible focus, semantic labels, modal focus restoration, reduced-motion behavior, responsive layouts down to 320px, and usable A4/Letter print output when touching relevant UI.
- Avoid new dependencies unless they materially simplify the design. Include dependency, bundle, security, and deployment implications in the HLD before adding one.
- Preserve existing user changes. Do not auto-resolve unrelated conflicts or reformat unrelated files.

## Verification

Use Node.js 24. Run the checks appropriate to the change, and run the full required suite before handing off a completed implementation:

```sh
rtk npm run lint
rtk npm run typecheck
rtk npm run validate:content
rtk npm run build
```

For content-generation changes, also run `rtk npm run generate:content` before validation and review the generated diff. For behavior changes, exercise the affected flow in the browser, including relevant keyboard, responsive, persistence, and print behavior. Do not claim automated coverage that the repository does not yet have; the deferred test suite and professional content review remain release blockers documented in `TODOS.md`.
